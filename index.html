En vivo Proyecto personal · 2026

Observatorio de Salud Pública de Antioquia

Pipeline de datos, API y página pública sobre los casos notificados al SIVIGILA en Antioquia entre 2007 y 2022.

  • Python
  • pandas
  • SQL
  • MySQL
  • FastAPI
  • pytest
  • Docker
  • GitHub Actions

Ver observatorio Código

Casos por año en Antioquia, 2007–2022

Cargando datos del observatorio…

  • 27.628

    El dengue llega en olas: epidemias en 2010 (25.804 casos) y 2016 (27.628).

  • 51 %

    Medellín concentra el 51 % del dengue del departamento.

  • −90 %

    La malaria vivax cayó casi 90 % entre 2010 y 2017: de 36.768 a 3.748 casos.

Problema
Los datos abiertos del SIVIGILA llegan como texto, con códigos de municipio incompletos y filas repetidas. Así no responden preguntas.
Qué construí
Un pipeline ETL en Python y pandas que descarga los datos de datos.gov.co, los limpia y valida, los carga en un modelo estrella en MySQL y los publica con una API de solo lectura en FastAPI y en la gráfica de esta página.
Decisiones técnicas
  • Códigos DIVIPOLA rellenados a 5 dígitos; los municipios desconocidos se conservan pero quedan fuera de los rankings.
  • Análisis en SQL con CTE y funciones de ventana (LAG, ROW_NUMBER) para calcular el canal endémico.
  • GitHub Actions corre las pruebas con pytest en cada push y actualiza los datos el día 1 de cada mes.
Resultado
1.185.468 casos notificados, limpios y publicados en un observatorio que se actualiza solo.
Mi rol
Proyecto personal: lo hice todo, de la extracción de los datos a la página publicada.

Qué aprendí

  • Los datos abiertos no responden preguntas tal como llegan: vienen como texto, con códigos de municipio incompletos y filas repetidas, y hay que limpiarlos y validarlos primero.
  • Automatizar las pruebas y la actualización mensual con GitHub Actions mantiene el observatorio al día sin trabajo manual.

Numi

Una app educativa que funciona sin internet, con un asistente de IA que corre en el propio celular, para niños de zonas rurales de Medellín.

  • Flutter
  • Dart
  • Riverpod
  • SQLite
  • Gemma 2B
  • TFLite
  • FastAPI
  • Firebase Auth

Ver código en GitHub

Problema
Muchos niños de primaria en zonas rurales de Medellín tienen poco o ningún acceso a internet, y casi todas las apps educativas lo necesitan.
Qué construimos
Una app en Flutter para niños de 1.° a 5.° de primaria: 15 actividades en las 5 materias del currículo colombiano, con audio en todas, y un asistente de IA que responde sin conexión.
Decisiones técnicas
  • MVVM con Riverpod: las vistas nunca tocan los datos, así el equipo de Ingeniería y el de Crosmedia trabajan en capas separadas.
  • El RAG siempre es offline: el celular es la fuente de verdad y Gemma 2B corre en el dispositivo.
  • El progreso se guarda en SQLite local, se sincroniza con un backend en FastAPI y se restaura al iniciar sesión en otro celular.
Estado
En desarrollo: el equipo sigue trabajando en la app. Funciona en celulares de 5 pulgadas y tablets de 10.
Mi rol
La arquitectura de la app, la lógica y las pantallas de Ciencias Naturales, el RAG offline del asistente y el diseño responsive de todas las pantallas.

Así responde el asistente sin internet

Todo ocurre en el celular, en modo avión

  1. entrada

    El niño pregunta

    Por ejemplo: ¿qué es una fracción?

  2. TFLite

    Embedding en el celular

    La pregunta se convierte en vector con un modelo en el dispositivo, con respaldo de bigramas.

  3. SQLite

    Búsqueda local

    BM25 y similitud coseno sobre vectores precalculados de la base de conocimiento.

  4. RAG

    Los 3 mejores fragmentos

    Los fragmentos más relevantes pasan al modelo como contexto.

  5. Gemma 2B

    Respuesta a su nivel

    El modelo corre en el celular y adapta la respuesta al grado del niño.

  • 100 %

    Offline una vez instalada: actividades, audio y asistente de IA.

  • 2 GB

    de RAM bastan: pensada para celulares Android 8+ de gama baja.

  • 15

    actividades en 5 materias, de 1.° a 5.° de primaria.

Qué aprendí

  • Separar las vistas de los datos con MVVM y Riverpod permite que dos equipos, Ingeniería y Crosmedia, trabajen en el mismo repositorio sin pisarse.
  • Diseñar para el celular más modesto (2 GB de RAM, sin internet) obliga a que todo, incluido el modelo de IA, corra en el dispositivo.

CineX

Sistema de gestión de cine: cartelera con películas reales de la API de TMDB, salas, funciones, venta de sillas, confitería, usuarios y reservas.

  • Java 21
  • Spring Boot

  • MySQL
  • JUnit
  • Postman
  • Swagger
  • Docker
  • GitHub Actions
  • HTML
  • CSS
  • JavaScript

Ver sitio Probar la API (Swagger) Código

La API está en un servidor gratuito; la primera carga puede tardar unos segundos.

Reglas que la API hace cumplir

  1. 409

    Nunca vende más sillas que la capacidad de la sala.

  2. 409

    Una sala no puede tener dos funciones a la misma hora.

  3. 400

    Los datos inválidos se rechazan indicando los campos que fallaron.

  4. 404

    Los recursos que no existen responden con un mensaje claro en JSON.

Problema
Un cine no puede vender sillas que no tiene ni programar dos funciones en la misma sala a la misma hora. La versión 1.0 guardaba películas, salas, funciones y compras en memoria: nada sobrevivía a un reinicio.
Qué construí
Una API REST en Java 21 con Spring Boot y MySQL, consumida por un frontend web en HTML, CSS y JavaScript.
Decisiones técnicas
  • Las reglas de negocio viven en la capa de servicios y responden 409 Conflict cuando se rompen.
  • Un solo formato de error para toda la API: JSON con estado, mensaje y ruta (400, 404, 409).
  • Docker Compose para el entorno local, CI con GitHub Actions y despliegue gratuito.
Resultado
Una API documentada y en línea, con 17 pruebas automáticas y una colección de Postman de 26 solicitudes.
Mi rol
v1.0 en equipo: estructura del repositorio, integración y revisión de pull requests. v2.0 individual: persistencia en MySQL, validaciones, manejo de errores, Swagger, 17 pruebas (JUnit + Mockito), colección de Postman de 26 solicitudes, Docker Compose, CI y despliegue.

Qué aprendí

  • Guardar los datos en memoria no basta: la versión 1.0 lo perdía todo en cada reinicio, por eso la 2.0 los llevó a MySQL.
  • Poner las reglas de negocio en la capa de servicios, con un solo formato de error (400, 404, 409), hace que la API sea predecible para quien la usa.
